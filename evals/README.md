# Проверка качества через Gemini

Набор содержит восемь небольших ТЗ с ручной разметкой ожидаемых конфликтов. В нём есть исходный сценарий покупки 31 января, согласованная версия этого сценария, учёт по дате проведения, ошибочный рост счётчика после перевода, перефразированный конфликт с другими датами, два чистых ТЗ и конфликт повторной заявки.

Из корня репозитория с настроенным `.env` выполните команду. Путь результата должен быть новым. Проверка обращается к Gemini и расходует квоту API.

```sh
.venv/bin/python -m evals.run --output ../kiker-eval --repeats 3 --baseline
```

Для короткой проверки двух вариантов покупки выполните следующую команду.

```sh
.venv/bin/python -m evals.run --output ../kiker-quick-check --repeats 1 \
  --case january-conflict --case january-corrected
```

Прогон сохраняет каждый отчёт и `results.json` с исходным SHA-256, версией кода, моделью, временем, числом запросов, токенами и найденными замечаниями. Ошибка API записывается как неуспешный прогон. Повторный запуск создаёт другую папку.

Успешный случай требует найти все размеченные противоречия с двумя нужными источниками, получить ноль лишних замечаний и ноль отклонённых записей. Код возврата 1 означает хотя бы один неуспешный случай KIKER. Baseline использует тот же Gemini, системные инструкции, схему и входные фрагменты в одном запросе. KIKER дополнительно выполняет отдельные проходы, подтверждение замечаний и детерминированную сверку поддерживаемых таблиц.

Это регрессионный набор с известными авторам ожидаемыми ответами. Его объём ограничивает выводы о качестве на новых документах. Для независимой оценки нужен дополнительный набор с разметкой системного аналитика.
